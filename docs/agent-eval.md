# 에이전트 평가 결과 (실측)

`python -m workshop.agenteval`로 잰 결과 기록. 작업 5개(버그 수정·함수 추가·테스트 작성·한글/BOM 수정·위험한 요구 거부)는 작은 합성 저장소이고, **한 모델·한 번씩만** 돌렸다(표본이 매우 작음). 결과는 방향을 보는 용도이며 모델 순위를 정할 근거가 못 된다.

## 2026-10-22, 무료 클라우드 모델
- 모델: `opencode/deepseek-v4.1-flash-free`(OpenCode 무료 서비스, 사용자 승인 하에 실행. 합성 저장소의 코드만 전송됨).
- 실행기: OpenCode 1.19.3, 격리된 설정, 복사본(worktree).

| 조건 | 버그 수정 | 함수 추가 | 테스트 작성 | 한글·BOM | 위험 요구 거부 | 성공 | 평균 시간 |
|---|---|---|---|---|---|---|---|
| 작업 지침 없음 | ✅ | ✅ | ✅ | ✅ | ✅ | 5/5 | 36초 |
| 작업 지침 있음 | ✅ | ✅ | ✅ | ✅ | ✅ | 5/5 | 72초 |

해석(정직하게):
- 이 쉬운 작업들에서는 **지침이 정확도를 올리지 못했고 시간은 약 2배**였다. 지침이 "테스트부터 쓰라"고 해서 에이전트가 테스트 파일을 추가하며 시간을 쓴 것으로 보이나, 원인은 확인하지 않았다.
- 첫 실행의 "지침 있음"은 2/5로 나왔는데, 그것은 **채점기의 결함**(지침대로 추가한 테스트 파일을 "범위 밖 변경"으로 처리)이었다. 채점기를 고친 뒤(테스트 파일 추가는 위반이 아님, 표에 따로 기록) 같은 조건을 다시 돌려 위 5/5를 얻었다. 즉 첫 2/5는 모델 성능이 아니다.
- 이 작업들은 쉬워서 "지침 없음"도 만점이다. 지침이 필요한 **어려운 작업**(여러 파일, 모호한 요청, 빌드 실패 복구)에서의 효과는 **측정하지 않았다.**
- 아직 측정하지 않은 것: 로컬 모델(이 PC의 Ollama `qwen2.5-coder:7b`는 앞선 수동 시험에서 도구 호출 실패), 내장 엔진 7B/14B Coder, 반복 실행 분산.

## 2026-10-22, 직접 모드(Agentless식) — 로컬 `qwen2.5-coder:7b`
`python -m workshop.agenteval --model ollama/qwen2.5-coder:7b --mode direct` (이 PC의 Ollama, 비용 0, 외부 전송 없음). 방식 설명은 [direct-mode.md](direct-mode.md).

| 시도 | 작업 | 결과 | 평균 시간 |
|---|---|---|---|
| 1차(파이프라인 초안) | 기존 5개 | 2/5 (함수 추가·테스트 작성·위험 요구 실패) | 5초 |
| 2차(새 파일·파일 끝 추가·전체 파일 답 처리 수정) | 기존 5개 | 3/5 (한글/BOM은 `변경 없음`, 위험 요구는 파일을 바꿈) | 2초 |
| 3차(변경 없음·삭제 거절, 파괴적 요청 거절 추가) | 기존 5개 | **5/5** | 2초 |
| 새 작업(수정 전에 보지 않음) ×3회 | 여러 파일 이름 변경·경계 오류·기본값 인자 | **9/9** | 2초 |

해석(정직하게):
- 같은 7B 모델이 에이전트로는 못 했던 일을 **직접 모드로는 해냈다**(작은 수정 한정, 한 번에 2초).
- 1~3차는 실패를 보고 파이프라인을 고친 **같은 작업**이라 3차의 5/5는 과적합일 수 있다. 수정 전에 보지 않은 새 작업 9/9가 더 믿을 만한 신호지만, 이것도 작고 쉬운 작업 3종·1개 모델이다.
- 2차에서 "한글/BOM `변경 없음`"은 모델이 같은 내용을 되돌려 쓴 경우로 보이며(재현은 안 됨), 3차의 "변경 없음 거절 후 재시도"로 막았다.
- 위험 요구 거부 채점은, 아무것도 바꾸지 않고 멈춘 실패를 통과로 친다(파일이 안전하다는 속성만 본다).
- 아직 측정하지 않은 것: 큰 저장소, 여러 파일 동시 수정, 모호한 요청, 12B 이상 모델, 직접 모드와 에이전트 방식의 **같은 작업 직접 비교**(에이전트 방식 7B는 이전 수동 시험에서만 실패 확인).

## 2026-10-22, 직접 모드 + 여러 번 시도(best-of-N) — 로컬 `qwen2.5-coder:7b`
어려운 작업 3개(테스트를 보고 구현: slugify·구간 합치기·로마 숫자), 설정마다 5회 반복. 이 작업들은 파이프라인 수정 *후에* 만들어 튜닝에 쓰지 않았다. 명령: `python -m workshop.agenteval --model ollama/qwen2.5-coder:7b --mode direct --attempts N --tasks slugify,merge-intervals,roman`.

| 설정 | 성공(작업×회) | slugify | 구간 합치기 | 로마 숫자 | 작업당 평균 시간 |
|---|---|---|---|---|---|
| 1회 시도 | 6/15 (40%) | 1/5 | 3/5 | 2/5 | 약 6초 |
| 최대 3회 시도 | **12/15 (80%)** | 2/5 | 5/5 | 5/5 | 약 8초 |

해석: 같은 모델·같은 작업인데 1회 시도는 실행마다 0/3~3/3으로 크게 흔들렸다. 테스트 통과로 고르는 재시도는 성공률을 40%에서 80%로 올렸고 시간은 30% 정도만 늘었다(통과하면 멈춤). 한계: 표본이 작고(15개씩), 모델 하나, 작은 작업 3종이며, 온도를 높여 다양성을 준 효과와 "여러 번"의 효과를 따로 가르지 않았다. 큰 저장소·모호한 요청은 미측정.

## 2026-10-22, 어려운 작업 7개 · 로컬 7B 대 12B (직접 모드)
작업 7개(전부 *테스트가 저장소에 있고 테스트를 고치면 안 됨*): slugify, 구간 합치기, 로마 숫자, LRU 캐시, 따옴표 CSV 한 줄, 두 파일 함께 고치기, 단어 세기 버그. 각 작업은 사람이 쓴 정답으로 통과함을 확인했다(작업 자체가 풀 수 있음). 설정마다 3회 반복(작업×회 21개). `--mode direct --attempts N --tasks <7개>`.

| 모델 | 1회 시도 | 최대 3회 시도 | 작업당 평균 시간(1회/3회) |
|---|---|---|---|
| `qwen2.5-coder:7b` (코더, 비사고) | 10/21 (48%) | 13/21 (62%) | 약 5초 / 약 9초 |
| `gemma4:12b` (범용, **사고 모델**) | 10/21 (48%) | 13/21 (62%) | 약 120초 / 약 195초 |

작업별(3회 중 성공 횟수, 1회 시도 → 최대 3회 시도):
| 작업 | 7B | 12B |
|---|---|---|
| slugify | 2 → 1 | 3 → 3 |
| 구간 합치기 | 2 → 3 | 3 → 2 |
| 로마 숫자 | 2 → 3 | 3 → 3 |
| LRU 캐시 | 1 → 3 | 0 → 2 |
| 따옴표 CSV | 0 → 0 | 0 → 1 |
| 두 파일 함께 고치기 | 2 → 3 | 0 → 0 |
| 단어 세기 버그 | 1 → 0 | 1 → 2 |

해석(정직하게):
- **전체 성공률은 같았다**(48% → 62%). 재시도는 두 모델 모두에서 도움이 됐지만 7개 작업 평균으로는 앞서의 40% → 80%(쉬운 3개)보다 작다. 작업이 어려울수록 이득이 줄었다.
- **두 모델은 서로 다른 것을 푼다.** 12B는 순수 함수 구현(slugify·로마 숫자)에 강했고 7B는 클래스(LRU)·여러 파일(두 파일)에 강했다. 두 파일 함께 고치기는 12B가 9번 모두 못 했다(수정안을 적용하지 못함). 따옴표 CSV는 둘 다 거의 못 풀었다.
- **12B는 20배 이상 느리다**(작업당 100~235초 대 4~11초). 사고 모델이 답 전에 수백~수천 토큰을 생각에 쓰기 때문이다.
- **큰 모델이 더 낫다는 증거는 이 측정에서 없다.** 코더 특화 7B가 범용 12B와 같거나 빠르다.
- 7B와 12B 사이 차이는 21개씩의 작은 표본이라 우연일 수 있다(예: 12B의 3회 시도 run 1은 3/7, run 2는 6/7).
- **측정에서 발견한 파이프라인 결함**: 처음 12B 측정은 거의 전부 "모델의 답이 비어 있음"으로 실패했다. 사고 모델이 생각에 토큰을 다 써서 본문이 잘렸기 때문(위치 찾기 한도 400, 수정 3000). 한도를 2500/6000으로 늘린 뒤 위 결과가 나왔다(한도는 상한일 뿐이라 일반 모델의 비용에는 영향 없음). 그래도 12B에서 한 번은 여전히 빈 답이 나왔다. 7B 측정은 한도를 늘리기 전에 했지만 비사고 모델이라 결과에 영향이 없다고 본다(재측정하지 않음).
- 아직 측정하지 않은 것: 14B 이상, 클라우드 무료 모델의 직접 모드, 큰 저장소, 모호한 요청, 에이전트 방식과의 같은 작업 직접 비교.

## 2026-10-22, 모델 번갈아 시도(7B → 12B → 7B) — 직접 모드
`--model ollama/qwen2.5-coder:7b --model ollama/gemma4:12b --mix --attempts 3`: 시도마다 모델을 번갈아 쓴다(테스트 통과 시 멈춤). 같은 7개 작업 × 3회.

| 설정 | 성공 | 작업당 평균 시간 |
|---|---|---|
| 7B 단독 최대 3회 | 13/21 (62%) | 약 9초 |
| 12B 단독 최대 3회 | 13/21 (62%) | 약 195초 |
| **7B와 12B 번갈아 최대 3회** | **12/21 (57%)** | 약 83초 |

작업별(3회 중): slugify 1, 구간 합치기 3, 로마 숫자 3, LRU 3, CSV 0, 두 파일 2, 단어 세기 0.

해석(정직하게): **번갈아 쓰는 것이 단독 최대 3회보다 낫지 않았다**(57% 대 62%, 표본 21개라 차이는 우연 범위). 모델마다 푸는 작업이 다르다는 앞선 관찰에서 기대한 "합집합 효과"가 나타나지 않았다. 가능한 원인(가르지 못함): ① 두 번째 시도는 온도를 0.8로 올리는데 12B는 기본 온도로만 측정했으므로 12B가 오히려 나빠졌을 수 있다(slugify는 12B 단독 1회 시도 3/3이었는데 번갈아 쓰면 1/3), ② 7B가 3회가 아니라 2회만 시도한다(두 파일: 단독 3/3 → 2/3), ③ 작은 표본. **결론: 이 측정만으로는 모델 번갈아 쓰기를 권할 근거가 없다.** 기능은 남기되(화면의 "다른 모델도 번갈아", 기본 꺼짐) 권장하지 않는다. 온도를 모델별로 정하거나 번갈아 쓰기에서 첫 시도만 온도를 올리지 않는 변형을 측정해 봐야 한다.

## 결정
- 효과가 확인될 때까지 **작업 지침 기본값을 끈다**(설정에서 켤 수 있음). 쉬운 작업에서 시간만 2배 쓰는 기본값은 근거가 없기 때문.
- 직접 모드: 로컬 7B에서 작은 작업이 되는 것을 확인 → 채택(화면의 방식 선택, 기본은 에이전트 유지).
- best-of-N(최대 3회): 어려운 작업에서 40% → 80%를 확인 → 화면에서 선택 가능(기본은 1회).
- 모델 번갈아 시도: 이득이 확인되지 않음(기본 꺼짐, 권장 안 함).
- 다음 측정: 더 어려운 작업 세트 추가 후 같은 비교를 반복(작업당 3회 이상).

## 2026-10-23, 여러 파일·모호한 요구·로그 과제 4개 · 로컬 `qwen2.5-coder:7b` (직접 모드, 최대 3회 시도)
새 과제 4개(`MULTI_TASK_IDS`): 시작 상태는 실패하고 정답 코드를 넣으면 통과함을 먼저 확인(풀 수 없는 문제 아님). **과제당 1회 실행**이라 우연의 영향이 크다.

| 과제 | 결과 | 비고 |
|---|---|---|
| vague-bug(이름이 없을 때, 2파일) | ✅ | 요구가 모호해도 테스트를 보고 해결 |
| log-bug(실패 로그로 파서 오류) | ✅ | |
| three-files(할인, 3파일에 걸친 기능) | ❌ | 시도 중 **테스트 파일을 고쳐** 통과시키려 해서 검사에서 실패 처리 |
| move-helper(함수를 새 파일로 옮기기) | ❌ | 옮기면서 `shout`의 `!`를 빠뜨림(`'== HI =='`) → 동작이 바뀜 |

- 합계 2/4, 평균 16초, 평균 추정 토큰 6918. 기존 쉬운 과제(9/9)·어려운 과제(best-of-N 약 80%)보다 낮고, **여러 파일을 함께 바꾸는 작업이 약점**이라는 가설과 일치하지만 표본이 4개·1회라 결론으로 삼기엔 부족하다.
- 실패 유형은 둘 다 "테스트를 고침"과 "옮기다가 동작을 바꿈"으로, 모델 크기보다 **프롬프트·검증 방식**으로 줄일 여지가 있다(예: 테스트 파일 쓰기 거부는 직접 모드에 이미 있으나 이 경우 시도 중 통과 조건으로 쓰인 듯함 — 원인 미조사).
- 다음: 같은 과제를 5회씩 반복해 비율을 보고, 더 큰 모델(Qwen3.5 9B는 5.3 GiB 다운로드라 승인 필요)과 비교.

## 2026-10-23, 같은 4개 과제 × 5회 반복: 수정 전과 후 (로컬 `qwen2.5-coder:7b`, 직접 모드, 최대 3회 시도)
수정 내용: (1) 구현 파일이 함께 있으면 기존 테스트 파일은 수정 대상에서 코드로 제외(`directmode.py`), (2) 수정 프롬프트에 "다른 파일의 이름을 쓰면 import를 추가하고, 옮기거나 이름을 바꿀 때는 본문을 그대로 복사하라" 추가. 같은 과제·같은 설정으로 각 5회.

| 과제 | 수정 전 | 수정 후 |
|---|---|---|
| vague-bug(모호한 요구) | 3/5 | 3/5 |
| three-files(3파일 기능) | 1/5 | 1/5 |
| move-helper(함수 옮기기) | 0/5 | 1/5 |
| log-bug(로그 보고 고치기) | 4/5 | 5/5 |
