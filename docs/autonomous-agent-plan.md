# 자율 코딩 에이전트 + Computer Use 통합 계획 (초안 1판, 2026-10-22)

사용자가 준 "JetAI Autonomous Coding Agent & Computer Use 통합 개발 마스터 프롬프트"(이하 **프롬프트**)를 현재 코드에 적용하기 위한 계획이다.
**조사 + 계획 문서이며 아직 구현을 시작하지 않았다.** 근거는 이 저장소의 실제 코드·문서와 이 PC에서 잰 결과다.
기존 계획(`coding-agent-platform-plan.md`, `multi-agent-plan.md`)과 겹치는 부분은 다시 쓰지 않고 연결한다.

## 0. 한눈에

| 프롬프트의 큰 덩어리 | 현재 | 판단 |
|---|---|---|
| A 코딩 에이전트(도구·루프·한도) | OpenCode 실행기 + **직접 모드(JetAI가 단계 진행)** + best-of-N, 승인·되돌리기·보고서 | 절반은 있음. **JetAI 자체 도구 계층과 일반 루프는 없음** |

| C 로컬 모델 런타임(사양 분석·추천·벤치) | 내장 엔진(llama.cpp+GGUF), `detect_hardware`, 모델 5종 표, 평가 하네스 | 절반 있음. 추천이 **실측 기반이 아님**, VRAM 관리 없음 |

| E 프로젝트 등록·세션 | 작업 기록(`coderuns/`)에 최근 폴더 목록 | **프로젝트 레지스트리 없음**, 세션 재개 없음 |

결론: **프롬프트의 방향은 지금 구조와 잘 맞는다**(복사본 격리, 승인, 로컬·무료 우선, 측정 중심). 가장 새로운 부분은 Computer Use이고, 이것은 의존성·안전 결정이 먼저 필요하다. 코딩 에이전트 쪽은 "이미 있는 직접 모드를 일반 루프로 키우는" 방식이 측정 근거상 가장 안전하다.

### 1-2. 에이전트 루프 (프롬프트 4절)
`PLAN → INSPECT → ACT → VERIFY → REFLECT → COMPLETE`는 직접 모드와 거의 같은 모양이다.

| 단계 | 직접 모드에서의 대응 |
|---|---|
| PLAN | 위치 찾기(어떤 파일을 고칠지) — 작업 분해·위험·비용 예상은 **없음** |
| INSPECT | 프로젝트 요약, 관련 테스트 문맥 |
| ACT | 수정안 적용 |
| VERIFY | 감지된 빌드·테스트 실행 |
| REFLECT | 실패 출력을 보여 한 번 고치기, 시도 N회 중 선택 |
| COMPLETE | 보고서·`metrics.json`, diff 검토 |

한도: 시간(OpenCode 20분)·파일 3개·시도 5회·재시도 1회는 있음. **단계 수·도구 호출 수·토큰·비용·동일 오류 반복 감지는 일반화돼 있지 않음.**

### 1-3. Computer Use (프롬프트 5~7절): ⬜ 전부 없음
- 브라우저: 수동 e2e(`scripts/e2e/*.js`, Node + playwright-core, CI 아님). 제품 기능이 아님.
- Windows UI 자동화·화면 입력·비전: 없음.
- 관련 기반: `websocket.py`(자체 구현, 서버 쪽), 로컬 엔진(llama.cpp, 이미지 입력 모델은 아직 목록에 없음).

### 1-5. 멀티 에이전트 (프롬프트 10절)

### 1-7. 이번 측정이 계획에 주는 근거
- 작은 로컬 모델은 **OpenCode 같은 도구 호출 에이전트를 못 몬다**, 하지만 **직접 모드(글로 답)** 로는 작은 수정이 된다(7B, 기존 5개 5/5, 보지 않은 쉬운 3개 9/9).
- 어려운 7개 작업에서 1회 48%, 최대 3회 62%(7B·12B 동일). 재시도는 도움이 되지만 작업이 어려울수록 이득이 줄었다. 모델마다 푸는 작업이 달랐다(모델 번갈아 시도의 근거).
- 7B와 12B를 번갈아 쓰는 시도는 12/21(57%)로 단독(62%)보다 낫지 않았다 → **"모델을 섞으면 합집합이 된다"는 가정은 근거가 없다**(온도 등 교란 가능, 미해결). 멀티 에이전트 단계(6)도 같은 원칙으로 측정 뒤에만 켠다.
- 사고(reasoning) 모델은 토큰 한도에 걸려 빈 답을 낸다 → 모델 메타데이터에 "사고 모델 여부"가 필요하다.

| D10 | **JetAI 안 도구 호출 방식** | 모델이 도구를 호출 | 약한 모델은 네이티브 도구 호출을 자주 틀림(측정) | **JSON 액션 프로토콜**: 모델은 한 번에 JSON 하나(`{"action":"read","path":...}`)만 답하고, JetAI가 검증·실행·결과를 다시 보여 줌. 네이티브 도구 호출이 되는 모델은 같은 프로토콜의 다른 전송 방식으로 추가 |

## 3. 설계 방침 (근거 기반)

1. **직접 모드를 일반 루프로 키운다.** 새 `workshop/agentloop.py`가 `PLAN→INSPECT→ACT→VERIFY→REFLECT→COMPLETE` 상태 기계를 돌고, ACT는 JSON 액션 프로토콜로 **도구 계층**을 호출한다. 직접 모드(위치 찾기→패치→테스트)는 이 루프의 "고정 계획" 프리셋으로 유지한다(회귀 기준선, 약한 모델용).
2. **도구 계층 `workshop/tools/`** (읽기·검색·패치·git·명령·브라우저·데스크톱). 도구마다 권한 종류(read/write/exec/gui/network)와 **정책 엔진**(현 `cmdguard`·`safe_path`를 확장해 한 곳에서 판단)을 거친다. 모든 호출은 **감사 로그**(JSONL, 비밀 가림)에 남긴다.
3. **한도 일반화**: 최대 단계·도구 호출·재시도·시간·토큰·비용, 같은 오류 반복 감지(같은 도구+같은 인자+같은 실패 3회면 멈춤). 한도 도달 시 상태를 저장하고 보고한다.
4. **Computer Use 3 백엔드**(같은 인터페이스):
   - A 브라우저: CDP(의존성 0). DOM·접근성 트리·스크린샷·콘솔·네트워크 오류.
   - B Windows UIA: PowerShell UIA + ctypes. 창 목록·요소 트리·포커스·클릭·입력·단축키.
   - C 비전: 스크린샷 → 로컬 VLM → 좌표. DPI 보정. **마지막 수단.**
   우선순위는 프롬프트와 같다(API·코드 > 터미널 > DOM > UIA > 비전). 단순 파일 수정에는 쓰지 않는다.
5. **관찰 → 목표 → 행동 → 확인** 사이클을 백엔드 공통 규칙으로 둔다: 행동 전 올바른 창·요소·클릭 가능 여부 확인, 행동 후 기대 변화 확인, **실패하면 같은 클릭을 반복하지 않고 다시 관찰**.
6. **프롬프트 인젝션**: 웹·README·터미널 출력·스크린샷 속 글은 모델에게 "데이터"로 감싸 전달하고(`<untrusted>` 구획), **행동 결정은 항상 JetAI 정책 엔진이 사용자 요청·허용 목록과 대조**한다. 읽은 글만으로 새 도구 권한이 생기지 않는다. 시험으로 검증한다(T14).
7. **모델 런타임**: `detect_hardware`를 확장(CPU·코어·드라이버·디스크·DPI·기존 모델 파일·WSL)하고, 모델 표에 코딩·한국어·**사고 모델 여부**·도구 호출·컨텍스트·백엔드 호환 메타데이터를 둔다. 추천은 **하네스 실측 표**(성공률·tok/s·메모리)를 우선한다. VRAM 관리는 "로드 중 모델 조회 → 필요 시 언로드 → OOM이면 컨텍스트 축소 후 재시도"까지.
8. **멀티 에이전트는 측정 뒤에 늘린다.** 단일 에이전트가 이기는 작업은 단일로(프롬프트 원칙과 같음). 병렬 쓰기는 파일 소유권이 겹치지 않을 때만, 아니면 직렬.
9. **프로젝트 레지스트리** `~/.agent-workshop/projects.json`: 이름·경로·원격·기본/작업 브랜치·언어·빌드/테스트/실행 명령(감지값 + 사용자 수정)·개발 서버 URL·지침 파일·허용 앱·권한 정책·최근 작업. 작업은 항상 해당 프로젝트의 복사본에서만, 경로 이탈은 승인.

## 7. 위험과 미해결

- **Computer Use는 되돌릴 수 없는 일을 만들 수 있다.** 그래서 관찰 → 승인 순, 허용 앱 목록, 긴급 중지를 먼저 검증하고 자동 모드는 마지막.
- **하네스 없이 믿지 않는다.** 새 루프는 "직접 모드보다 나쁘지 않음"을 로컬 7B로 확인한 뒤 기본값으로 삼는다.
- **약한 모델의 한계**: 어려운 작업은 40~60%대. 에이전트 수를 늘린다고 해결되지 않는다(측정). 사용자에게 성공률을 솔직히 보여 주는 화면(작업 유형별 실측)을 계획에 포함한다(5단계).
- **브라우저·UIA의 환경 의존**: 이 대화의 환경에서는 Windows 앱 실조작과 사용자 PC 화면을 자동 검증하기 어렵다. 3·4단계는 **사용자 PC에서의 확인**을 완료 기준에 넣는다.
- **JetStudio 접근**은 사용자의 경로·승인이 필요하다(이 세션은 JetStudio 폴더를 모른다).
- **정직한 보고 규칙**: 코드가 있다고 완료로 표시하지 않고, 하네스·테스트·사용자 PC 확인의 세 단계(`verification.md`)를 구분해 기록한다.
