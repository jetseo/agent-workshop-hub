# 직접 모드 (Agentless식) — 약한 모델도 쓰는 코드 수정

OpenCode 같은 에이전트는 모델이 **도구 호출**(파일 읽기·수정·명령)을 정확히 해야 한다. 이 PC의 7B·12B 로컬 모델은 그걸 자주 틀려서 에이전트로 못 썼다. **직접 모드**는 순서를 JetAI가 정하고 모델에게는 **글로 답만** 받는다. 근거와 설계는 [multi-agent-plan.md](multi-agent-plan.md) M1(Agentless 논문 방식).

## 흐름 (화면: 코드 → 방식 "직접 모드")
1. **위치 찾기**: 파일 목록 + 프로젝트 요약 + 요청을 주고 모델이 고칠 파일(최대 3개, 새 파일 포함)을 JSON으로 답한다. JetAI가 실제 존재·경로를 검사한다. 파괴적 요청(삭제·초기화)이면 모델이 `{"refuse": true}`로 거절한다.
2. **수정안**: 파일마다 모델이 `SEARCH/REPLACE` 블록을 글로 쓴다. JetAI가 복사본에 **직접 적용**한다(찾는 글이 정확히 한 번 나올 때만, 줄 끝 공백 차이는 허용, BOM·줄바꿈(CRLF) 보존). 새 파일은 코드 블록 전체를 받는다.
   - 안 맞으면 이유를 알려 **한 번만** 다시 받는다. 모델이 블록 대신 파일 전체를 써 오면 작은 파일에 한해 받아들인다(diff로 결과를 확인). 파일이 바뀌지 않았거나 내용 대부분을 지우는 수정은 거절한다.
3. **테스트**("테스트로 확인" 체크 시): JetAI가 감지된 빌드·테스트 명령을 복사본에서 직접 실행(셸 없음·최소 환경·5분 제한, 수동 검사와 같은 실행기).
4. **고치기**: 테스트가 실패하면 실패 출력을 모델에게 보여 **한 번만** 더 고치게 하고 다시 테스트.
끝나면 에이전트 방식과 똑같이 diff 검토 → 적용/되돌리기/버리기, 보고서, 코드 리뷰를 쓴다.

## 여러 번 시도해서 고르기 (best-of-N, 화면의 "최대 N회 시도")
같은 일을 **서로 다른 복사본**에서 최대 N번(1~5) 시도한다. 첫 시도는 기본 온도, 이후는 조금 높은 온도로 달라지게 한다. **테스트가 통과하는 첫 시도에서 멈추므로**(토큰 절약) 쉬운 일은 1번으로 끝난다. 끝까지 통과가 없으면 점수로 고른다: 테스트 통과 > 실행할 테스트가 없음 > 테스트 실패 > 파이프라인 실패, 같으면 **바뀐 줄이 적은 것**, 그래도 같으면 먼저 한 시도. 고른 복사본만 남기고 나머지는 지우며, 시도별 결과(`attempts_log`)가 화면 타임라인·보고서에 남는다. 테스트로 고르므로 "테스트로 확인"이 꺼져 있으면 쓸 수 없다.
- 모델이 시도마다 **프로젝트의 테스트 파일을 읽기 전용 문맥**으로 받는다(8천 자까지). 무엇을 기대하는지 알아야 구현할 수 있기 때문.
- 지금은 **직렬**이다(로컬 모델은 한 번에 하나). 무료 클라우드 서비스끼리 병렬로 돌리는 것은 한도 문제가 있어 아직 만들지 않았다.
- 한도를 더 쓴다: 최악의 경우 N배. 무료 한도 보호(Mercury 등)와 서비스 한도가 먼저 막는다.

## 사고(reasoning) 모델 주의
`gemma4`처럼 답하기 전에 생각을 길게 하는 모델은 토큰 한도가 작으면 **본문이 비어서** 돌아온다(측정: 한 줄 답에 약 800토큰을 생각에 씀). 직접 모드의 답 한도는 위치 찾기 2500, 수정·새 파일 6000토큰으로 넉넉히 잡았다(한도는 상한일 뿐 일반 모델에는 비용이 없음). 사고 모델은 느리다(7개 작업에 모델당 100~235초 대 7B의 4~11초).

## 모델 번갈아 시도
화면의 "다른 모델도 번갈아"(시도 2회 이상일 때) 또는 API `models`로, 시도마다 다른 로컬·무료 모델이 맡게 할 수 있다(첫 모델 → 둘째 → 첫째 …, 최대 3개, 모두 비용·동의 검사). **측정 결과 이득이 없었다**(7B+12B 12/21, 단독 최대 3회 13/21) — 기본 꺼짐이고 권장하지 않는다. 자세한 해석은 [agent-eval.md](agent-eval.md).

## 안전
- 모델은 명령을 실행하지도, 복사본 밖을 건드리지도 못한다. JetAI가 글을 적용할 뿐이고, 경로는 복사본 안 상대 경로만(`..`·절대 경로·`.git`·비밀 이름 거부), 파일 삭제는 지원하지 않는다.
- 연결한 서비스(채팅 호출 경로)만 쓴다: **무료 한도 보호(Mercury 3 등)도 그대로 적용**된다. OpenCode 자체 모델은 못 쓴다. 유료일 수 있는 모델은 비용 확인이 필요.
- 한 번에 파일 3개·파일당 4만 자까지(더 크면 거절). 요청마다 모델 호출은 보통 2~4회.
- 한계: 큰 리팩터·여러 단계 추론·새 라이브러리 설치가 필요한 일은 맞지 않는다(에이전트 방식 또는 사람). 의존성 설치는 하지 않는다.

## 실측 (2026-10-22, 이 PC의 로컬 `qwen2.5-coder:7b`, Ollama, 비용 0·외부 전송 없음)
- **에이전트 방식**: 이전 수동 시험에서 파일 수정 도구 호출을 틀려 실패(`code-work.md`).
- **직접 모드**: 하네스의 작업 5개 → 처음 2/5 → **실패 원인을 보고 파이프라인을 고친 뒤 5/5**(평균 2초). 고친 점: 새 파일을 `files`에 넣어 오는 답 처리, 빈 SEARCH는 파일 끝에 추가, 변경 없음·내용 삭제 거절, 파괴적 요청 거절.
- **여러 번 시도(best-of-N), 더 어려운 작업 3개**(테스트를 보고 구현: slugify·구간 합치기·로마 숫자. 파이프라인을 고친 뒤에 만든, 튜닝에 쓰지 않은 작업) × 5회씩, 같은 7B 모델:

| 설정 | 성공(작업×회) | 작업별 (slugify / 구간 합치기 / 로마 숫자) | 평균 시간(작업당) |
|---|---|---|---|
| 1회 시도 | 6/15 (40%) | 1/5 · 3/5 · 2/5 | 약 6초 |
| 최대 3회 시도 | **12/15 (80%)** | 2/5 · 5/5 · 5/5 | 약 8초 |

  해석: 약한 모델은 **실행마다 결과가 들쭉날쭉**하고(1회 시도는 같은 작업이 0/3, 3/3으로 오감), 테스트로 고르는 재시도가 성공률을 크게 올렸다(40% → 80%). 시간은 약 30%만 늘었다(통과하면 멈추므로). slugify는 3회 시도로도 2/5라 이 모델에는 어렵다.
- **정직한 주의**: 위 5/5는 *고치는 데 쓴 바로 그 작업들*이라 과적합일 수 있다. 그래서 **고치기 전에 보지 않은 새 작업 3개**(여러 파일 이름 변경, 경계 오류, 기본값 인자 추가)를 추가해 3회 반복했고 **9/9**였다. 이 작업들도 작고 쉽다. 큰 저장소·모호한 요청·여러 파일 변경은 아직 **측정하지 않았다**. 자세한 표는 [agent-eval.md](agent-eval.md).
