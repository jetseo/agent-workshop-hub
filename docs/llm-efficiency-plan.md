# LLM 효율 활용 계획 (초안 1판, 2026-10-22)

"JetAI 로컬 코딩 에이전트 통합 개발 마스터 프롬프트"(이하 **프롬프트**)를 바탕으로, **무료 로컬 LLM을 가장 적은 토큰·시간·메모리로 쓰는 방법**을 정리한 계획이다. 조사+계획 문서이며 구현은 시작하지 않았다. 모든 숫자는 이 PC에서 직접 잰 것이거나 출처를 밝힌 것이고, 확인하지 못한 것은 `UNVERIFIED`로 적었다.
관련 문서: [autonomous-agent-plan.md](autonomous-agent-plan.md)(단계·결정), [direct-mode.md](direct-mode.md), [agent-loop.md](agent-loop.md), [agent-eval.md](agent-eval.md)(실측표), [multi-agent-plan.md](multi-agent-plan.md).

## 0. 한 줄 요약
**가장 큰 낭비는 모델을 더 많이 쓰는 것이 아니라 (1) 모델이 보지도 못하는 입력을 보내는 것, (2) 한 번에 한 가지만 시키면 되는 일을 여러 턴 대화로 시키는 것, (3) 측정 없이 모델을 고르는 것**이다. 이번 세션 측정으로 세 가지 모두 근거가 생겼다.

## 2. 이미 있는 효율 장치 (재사용, 새로 만들지 않음)
- **질문 분류·모델 선택**: `arbiter.py`(코드/일상/조사 + 난이도), `router.py`(로컬·무료만, 쿨다운·부하 분산·실패 시 전환), `runstats.py`, `modelpick.py`·`modelinfo.py`(이름·공개 벤치로 등급 추정), `usage.py`(토큰 장부).
- **토큰 절약기**: `digest.py`(긴 글 압축), `logsum.py`(로그 축약), `cache.py`(같은 입력 결과 캐시).
- **코드 작업 쪽**: 프로젝트 요약·관련 테스트만 문맥으로(`projectmap`, `directmode.related_tests`), **테스트가 통과하는 첫 시도에서 멈춤**(best-of-N), 루프의 단계·도구·토큰·시간·반복 실패 한도, 오래된 교환 요약.
- **하드웨어**: `engine.detect_hardware`(RAM·GPU 이름·VRAM), `engine.fit`(VRAM·RAM으로 GPU/CPU/불가), 모델 5종 표, "한 번에 모델 하나"(엔진).
- **무료·유료 방어**: 유료 자동 전환 없음, 무료 한도 가드.

## 3. 이번 세션 실측이 말해 주는 것 (이 PC: RTX 3060 12GB, 로컬 Ollama)
| # | 사실 | 근거 | 의미 |
|---|---|---|---|
| F1 | **짧은 단일 목적 질문(직접 모드)이 여러 턴 대화(액션 루프)보다 4~6배 싸고 더 잘 풀림** | 7B, 어려운 7개 작업: 직접 7/21·약 2,500토큰 대 루프 0~2/21·8,900~16,000토큰 | 약한 모델에는 "한 번에 한 가지"가 기본 |
| F2 | **재시도 + 테스트 선별**은 성공률을 크게 올리고 시간은 조금만 늘림 | 쉬운 3개 40%→80%(+30% 시간), 어려운 7개 48%→62%(+80% 시간) | 통과하면 멈추는 구조가 핵심 |
| F3 | **12B 사고 모델은 20배 느린데 성공률은 같음** | 7B 약 5초 대 12B 약 120초/작업, 둘 다 48%→62% | 큰 모델 ≠ 효율. 비용 대비 성공률로 골라야 함 |
| F4 | **사고(reasoning) 모델은 토큰 한도가 작으면 빈 답** | `gemma4:12b`가 한 줄 답에 약 800토큰을 생각에 씀 | 모델 메타데이터에 "사고 모델" 플래그와 예산 필요 |
| F5 | **서로 다른 모델을 번갈아 쓰는 것은 이득 없음**(교란 가능) | 7B+12B 12/21 대 단독 13/21 | "섞으면 합집합"은 가정일 뿐 |
| F6 | **Ollama가 긴 입력을 조용히 자름** | 이 PC의 기본 설정에서 1.5만 자·3.1만 자 프롬프트 모두 `prompt_tokens`가 **2050**(두 모델 모두). 문맥 16384로 만든 변체는 1.3만 토큰 전부 받음(`OLLAMA_CONTEXT_LENGTH` 미설정) | **지금까지 로컬 측정은 2K 입력 한도에서 이뤄졌다.** 위험은 실재하지만, **이 작은 작업들에서는 결론이 바뀌지 않았다**(아래 5절 재측정). 큰 프로젝트·긴 테스트 문맥에서는 영향이 클 수 있어 L0·L1이 필요 |

> **F6 영향 재측정(문맥 16K 변체, 7B, 어려운 7개, 1회 시도, 3회 반복)**: 직접 모드 **8/21**(기본 문맥 7/21), 액션 루프 **1/21**(기본 문맥 0~2/21). 추정 토큰은 직접 약 2,200~4,000, 루프 약 9,400~10,300으로 같았다. **차이는 우연 범위**라서 "잘림이 루프를 망쳤다"는 가설은 **기각**, 루프가 약한 원인은 프로토콜·모델이다. 이 작업들의 프롬프트가 대부분 2K토큰 안에 들어와서일 수 있어, 큰 입력에서의 영향은 **여전히 미측정**이다. (측정용 임시 모델 변체는 만들었다가 삭제했고, 사용자의 Ollama 모델 목록과 설정은 그대로다.)

## 4. 프롬프트 대비 갭과 판단
프롬프트가 요구하는 것 중 **이미 있는 것**: 프로젝트 파일 탐색·선택적 컨텍스트(`projectmap`), 승인 후 변경·되돌리기, 빌드/테스트 실행·로그 수집(`checks`), 재시도 한도, 모델 자동 선택의 뼈대(`arbiter`/`router`), 하드웨어 분석·적합성 판정(`engine`), 성공률 기록 뼈대(`runstats`), 실제 작업 기반 평가(`agenteval`), 취소·타임아웃·감사 로그.
**없는 것**: ① 입력 토큰 실측과 잘림 감지 ② KV 캐시·실행 버퍼를 포함한 메모리 추정과 문맥 길이 선택 ③ 모델×작업 유형별 누적 성공률로 하는 라우팅(+표본 부족 처리) ④ 모델 로드·전환 비용 측정과 언로드 정책 ⑤ 사고 모델 예산 ⑥ 후보 모델(아래 표)의 메타데이터·실측 ⑦ llama.cpp 직접 제어(문맥·오프로딩; 지금은 Ollama가 정함) ⑧ Reviewer/Planner 역할의 비용 대비 효과.
**충돌 우려 없음**: 모두 추가 모듈이거나 기존 모듈의 옵션이다. 진행 중인 PR 묶음(#35~#39)과 같은 파일(`codework.py`, `chat.py`)을 건드리는 항목은 그 PR이 병합된 뒤에 시작한다.

## 5. 효율 전략 (우선순위·근거·측정 방법)
각 항목은 **작은 PR + 하네스 전후 비교**로만 채택한다(안 좋아지면 되돌림). "기대"는 가설이다.

| 순위 | 전략 | 근거 | 기대 | 측정/수용 기준 |
|---|---|---|---|---|
| L0 | **계량 먼저**: `chat()`이 서비스가 알려 준 `usage`(입력·출력 토큰)를 함께 돌려줌, 코드 작업 호출을 `runstats`·`usage`에 **작업 유형·모델·토큰·시도 수**로 기록. 입력 토큰이 추정보다 현저히 작으면 **"입력이 잘렸을 수 있음" 경고** | F6 | 보이지 않던 낭비·잘림이 보임 | 가짜 서버 테스트 + 이 PC에서 잘림 경고가 실제로 뜸 |
| L1 | **문맥 길이를 우리가 정함**: 내장 엔진은 `llama-server -c N`을 직접 설정, Ollama는 모델 변체/환경 변수 안내(사용자 설정을 바꾸지 않고 **진단만** 먼저). 직접 모드는 입력 크기를 재서 문맥에 맞춰 줄이는 쪽을 우선(관련 테스트 문맥 줄이기) | F6 | 잘림으로 인한 실패 제거 | 같은 작업을 문맥 2K/8K/16K로 재측정(5절) |
| L2 | **프롬프트 앞부분 고정**(시스템 지시·프로젝트 요약을 앞, 작업을 뒤): llama.cpp·Ollama의 접두부 KV 캐시 재사용 | 일반 지식(서버 측 prompt cache) — **이 PC에서 속도 이득은 미측정** | 같은 프로젝트의 연속 작업 속도↑ | 연속 5개 작업의 평균 시간 전후 비교 |
| L3 | **필요한 문맥만**: 대상 모듈을 import하는 테스트만, 실패 로그는 `logsum`으로 줄여 복구 프롬프트에 사용, 검색→관련 파일만(전체 저장소 금지) | F1 | 입력 토큰↓ 성공률 유지 | 토큰/작업 전후, 성공률 동일 이상 |
| L4 | **사고 모델 예산·모드**: 모델 메타데이터에 `reasoning` 플래그, 사고를 줄이는 옵션이 있으면 사용(서비스가 지원하는 경우만, `UNVERIFIED`), 없으면 출력 한도를 넉넉히 | F4 | 빈 답 제거, 12B 시간↓ | 12B 작업당 시간 전후 |
| L5 | **하드웨어 인식 적합성**: `fit()`을 가중치 + **KV 캐시(문맥×층×헤드 차원)** + 실행 버퍼 + 안전 여유로 확장, GPU 사용 중 메모리를 반영, Windows/WSL 메모리 구분, 모델 로드 실패 시 더 작은 양자화/모델 제안 | 프롬프트 5절 | 로딩 실패·오프로딩 느림을 사전에 피함 | 이 PC에서 모델 5종 예측 대 실제(`nvidia-smi`) 오차 |
| L6 | **모델 전환 비용을 알고 배치**: 모델 교체 시간(로드·언로드)을 측정, 작은 작업은 모음 처리해 교체를 최소화, 일정 시간 안 쓰면 메모리 해제 | 프롬프트 5절, F3 | 전환 낭비↓ | 7B↔12B 교체 시간 실측 |
| L7 | **측정 기반 라우팅**: 모델×작업 유형별 성공률·시간·토큰을 쌓아 "성공 확률 ÷ 기대 시간"으로 고름, **표본이 적으면 점수를 내지 않고 보수적 기본값**(프롬프트 요구), 사용자 수동 지정 우선 | F2·F3, `runstats` | 쓸모없는 큰 모델 호출↓ | 라우팅 전후 총 시간·성공률(오프라인 재생으로 시뮬레이션) |
| L8 | **작게 시작, 검증된 실패에서만 올리기(캐스케이드)**: 작은 모델 → 테스트 실패 시 큰 모델. **F5의 교란(두 번째 시도 온도 0.8)을 고쳐서 다시 측정**한 뒤에만 채택 | F5 | 비용 절감 가능성 | 7B→12B 캐스케이드 대 단독, 온도 고정 |
| L9 | **역할(Planner·Reviewer)은 필요할 때만**: 테스트가 있고 통과하면 리뷰 생략, 큰 변경·테스트 없음일 때만 리뷰. 한 모델로 여러 역할 수행이 기본 | 프롬프트 8절, F1 | 토큰↓ | 리뷰 유무에 따른 결함 탐지율/비용(미측정) |
| L10 | **어려운 작업은 일찍 알림**: 난도·프로젝트 크기로 "로컬 모델로 성공 확률 낮음"을 시도 전에 안내(측정 데이터가 쌓인 뒤) | F2 | 헛돌기 방지 | 데이터 충분 시에만 |

**하지 않는 것**: 여러 모델 동시 상주(12GB VRAM), 측정 없는 점수 표시, 미설치 모델 자동 다운로드, 유료 API 자동 호출, 전체 저장소를 매번 프롬프트에 넣기.

- 5종을 모두 받으면 약 **59GiB**다. **전부 받지 않는다.** 우선 Qwen3.5 9B(5.3GiB)와 GPT-OSS 20B(10.8GiB)처럼 12GB에 가까운 것부터 사용자 승인 후 1~2개만 측정한다.
- 현재 내장 엔진의 모델 표(`engine.CATALOG`)는 5종(Qwen2.5 0.5B·1.5B·7B·Coder 7B·Coder 14B)이다. 새 모델은 표에 **메타데이터만 먼저** 추가(다운로드는 별도 승인, "측정 전" 표시).
