# 에이전트 분업·병렬 구조 조사와 적용 계획 (2026-10-22)

질문: 코드 작업을 쪼개 여러 에이전트에게 나누고(데이지 체인 같은 연결 구조), 병렬로 돌리면 무료·약한 모델로도 더 잘할 수 있지 않을까?
결론부터: **일부는 가능하고 일부는 오히려 해롭다.** 그냥 "에이전트를 여러 개 동시에"는 코딩에서 자주 실패하고, **"여러 개를 따로 시도하게 하고 테스트로 고르는 것"과 "고정된 단계로 쪼개기"는 약한 모델에 특히 잘 맞는다.** 아래는 근거와, 그에 따른 단계별 계획이다. 효과는 모두 **평가 하네스로 재서 확인한 뒤에만** 켠다(지금은 측정 전).

## 쉬운 설명: 구조 4가지
1. **체인(데이지 체인, 파이프라인)**: 계획 → 수정 → 테스트 → 리뷰처럼 앞 단계의 결과를 다음 단계가 받는다. 각 단계를 **다른 모델**이 맡을 수 있다(계획은 똑똑한 모델, 수정은 빠른 모델). 병렬이 아니라 *직렬*이라 충돌이 없다.
2. **지휘자-일꾼(오케스트레이터-워커)**: 지휘자가 일을 독립된 조각으로 나누고, 일꾼들이 각자 **자기 복사본**에서 동시에 처리한 뒤 합친다.
3. **여러 번 시도해서 고르기(best-of-N)**: 같은 일을 서로 다른 복사본에서 N번(다른 모델 또는 같은 모델 여러 번) 시도하고, **테스트 통과 여부로 최고를 고른다.** 쓰기는 각자 복사본이라 서로 안 부딪힌다.
4. **읽기 전용 탐색 병렬**: 파일을 *읽고 요약*하는 조사원 여러 명을 동시에 돌려 지휘자에게 보고. 아무것도 고치지 않아서 안전하다.

정리: 조사·탐색은 병렬이 이득, **코드 쓰기는 직렬이 기본, 병렬은 "서로 독립인 조각" 또는 "같은 일을 따로 시도 후 선별"일 때만**.

## 우리 제약
- **로컬 모델은 한 번에 하나**(VRAM). 로컬은 병렬이 안 되고, 병렬은 **클라우드 무료 서비스**끼리만 가능하며 분당·일일 한도에 걸린다(한도는 서비스마다 다름).
- 약한 모델은 **도구 호출을 자주 틀림**(시험에서 확인). 그래서 도구 호출이 필요 없는 구조(Agentless식)가 유리.
- 병렬은 토큰을 N배 쓴다. 무료 한도 안에서만, **유료는 자동 금지**(기존 규칙).
- 아직 **어떤 모델이 어디까지 되는지 측정 전**(평가 하네스 실행 중). 아래 모든 단계는 측정으로 이득이 보일 때만 기본값으로 켠다.

## 단계별 계획 (각각 작은 PR, 하네스로 전후 비교)
| 단계 | 내용 | 병렬? | 기대 | 위험 |
|---|---|---|---|---|
| **M0 측정(진행 중)** | 하네스로 현재 단일 에이전트의 성공률 측정(무료 클라우드, 지침 있음/없음) | — | 기준선 | — |
| **M1 직접 모드(Agentless식)** ✅ 구현됨(2026-10-22, [direct-mode.md](direct-mode.md)) | JetAI가 ①위치 찾기(저장소 지도+파일 후보를 모델에게 묻기) ②모델에게 **수정안을 diff/치환 형식 텍스트로** 받기 ③JetAI가 복사본에 적용 ④빌드·테스트(P1-2)로 판정. 도구 호출 불필요 | 직렬 | **로컬·약한 모델도 에이전트 없이 작은 수정 가능** | 큰 작업엔 부정확, 형식 파싱 실패 처리 필요 |
| **M2 여러 번 시도(best-of-N)** ✅ 직렬 구현·로컬 7B 실측(40%→80%, [direct-mode.md](direct-mode.md)), 병렬은 미구현 | M1의 ②를 N번(서로 다른 복사본) → 테스트 통과·변경 범위·리뷰(P1-3)로 점수 → 최고 하나만 사용자에게 제시. 먼저 직렬, 이득이 보이면 클라우드 무료끼리 병렬 | 병렬(읽기·시도) | 약한 모델의 성공률을 확률적으로 끌어올림 | 한도 소모 N배, 테스트가 약한 프로젝트에선 선별이 부정확 |
| **M3 분할 실행(오케스트레이터)** | 목표 입력 오케스트레이터(P1-1)가 계획 → **서로 다른 파일을 건드리는 독립 조각만** 병렬 worktree로 → 순서대로 병합 + 테스트. 파일이 겹치면 자동으로 **직렬로 되돌림** | 조건부 병렬(쓰기) | 큰 작업 시간 단축 | 의미 충돌, 병합 실패. 지휘자 지시문 품질에 좌우 |
| **M4 읽기 전용 조사원** | 큰 저장소에서 영역별 요약을 병렬로 만들어 지휘자·일꾼 맥락에 제공 | 병렬(읽기) | 맥락 길이 한계 완화 | 요약 오류가 전파 → 원문 위치를 같이 전달 |
| **체인(역할 분담)** | 계획(큰 모델)→수정(빠른 모델)→리뷰(다른 모델). 자동 모델 선택(arbiter)이 단계별로 모델 배정 | 직렬 | 모델 강점 분업 | 단계마다 지연·한도 소모 |

공통 안전 규칙(기존 유지): 쓰기는 항상 각자 일회용 복사본, 적용은 사람, 유료 자동 호출 금지, 승인된 명령만, 한 번에 로컬 모델 하나, **병렬 수 상한**(기본 2~3, 서비스 한도에 따라 낮춤), 한도 오류가 나면 병렬을 줄이고 직렬로.

## 권장 순서와 이유
1. **M0** 결과로 "단일 에이전트가 어디서 막히는지" 확인(진행 중).
2. **M1 → M2**를 먼저. 이유: 약한·무료 모델의 가장 큰 약점(도구 호출)을 피하고, 병렬의 이득(여러 번 시도)을 **충돌 위험 없이** 얻는다. 하네스로 단일 에이전트와 직접 비교.
3. **M3**는 P1-1(오케스트레이터)과 함께. M2에서 이득이 확인되면 진행.
4. M4는 큰 저장소에서 맥락 부족이 실제로 문제로 측정될 때만.

## 하지 않는 것
- "에이전트 N개가 같은 폴더를 동시에 편집" — 충돌·의미 불일치(Cognition의 지적).
- 외부 프레임워크(LangGraph·crewAI·MetaGPT 등) 도입 — 의존성·공급망 위험, 가치 대비 과함.
- 측정 없이 병렬·분업이 더 낫다고 단정.

## 한계 (이 조사의 신뢰도)
- Anthropic 글은 원문을 읽었다. Cognition·worktree 글은 검색 요약과 일부 원문 발췌 기반이라 세부 문구는 원문 확인이 필요하다. Anthropic의 "15배 토큰", "90% 개선" 수치는 **리서치** 작업 기준이며 코딩에 그대로 적용되지 않는다.
- 블로그·벤더 글(MindStudio, Augment 등)은 홍보 성격이 있어 참고용이다.
