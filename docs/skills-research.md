**라이선스 방침**: MIT·Apache-2.0은 고지만 지키면 재사용이 가능하지만, JetAI는 **방법론(아이디어)을 읽고 자체 한국어 문구로 다시 쓴다**. 문장·코드를 복사하지 않으므로 별도 고지 의무는 없지만, 출처 존중으로 이 문서에 이름을 남긴다. 라이선스가 없거나 불명확한 것은 내용을 쓰지 않는다.

## 읽은 스킬에서 뽑은 원칙 (우리 말로)
1. **고치기 전에 원인부터**(체계적 디버깅): 오류 메시지를 끝까지 읽고, 재현하고, 최근 변경을 보고, 증상이 아니라 원인 위치에서 고친다. 실패한 수정을 반복하지 않는다.
2. **테스트 먼저, 실패 확인**(TDD): 새 동작/버그는 먼저 실패하는 작은 테스트를 쓰고 *실패하는 것을 확인*한 뒤 최소한의 코드로 통과시킨다. 테스트가 이미 통과하면 테스트가 잘못된 것이다.
3. **증거 없이 "됐다"고 말하지 않는다**(완료 전 검증): 완료를 주장하기 전에 해당 명령을 새로 돌려 출력을 읽는다. "아마", "될 것이다"는 금지. 린트 통과 ≠ 빌드 통과. 에이전트의 "성공" 보고도 diff로 직접 확인.
4. **작은 단계, 확인 가능한 결과**(계획 작성): 파일과 이름을 먼저 정하고, 단계마다 "실행하면 확인되는 결과"가 있게 쪼갠다. 중복 금지(DRY), 필요 없는 건 안 만들기(YAGNI).
5. **한 번에 하나, 범위 지키기**: 요청과 무관한 파일·리팩터를 건드리지 않는다. 기존 코드의 방식과 이름을 따른다.
6. **리뷰 지적은 검증 후 반영**(리뷰 수신): 지적을 바로 따르지 않고 코드로 사실인지 확인, 불명확하면 먼저 묻고, 한 항목씩 반영하며 테스트한다. 빈말 맞장구 금지.
7. **격리된 작업 공간**(worktree): JetAI는 이미 일회용 worktree를 쓴다.
8. **독립 작업은 병렬 에이전트로**: JetAI는 한 번에 모델 하나라는 제약이 있어 보류(P2).

## JetAI에 적용하는 방법 (설계안, 아직 코드 아님)
- 에이전트 요청 끝에 **"작업 지침" 블록**(약 600~900자)을 붙인다. 위 1~3, 5의 핵심만 담는다: ① 수정 전에 관련 파일과 오류를 먼저 읽는다 ② 버그 수정/새 기능은 테스트를 먼저 추가하거나 기존 테스트로 실패를 확인한다 ③ 요청 범위 밖은 건드리지 않는다 ④ 끝나기 전에 허용된 테스트 명령을 실제로 돌려 결과를 확인한 뒤 "무엇을 바꿨고 무엇을 돌렸는지" 짧게 보고한다. 프로젝트에서 감지한 빌드·테스트 명령(P0-6)을 지침에 구체적으로 넣는다.
- 이미 JetAI 쪽에서 하는 것: 프로젝트 읽기, 격리, 빌드·테스트 직접 실행(P1-2), 다른 모델의 리뷰(P1-3), 승인(P0-3). 지침은 이것들과 겹치지 않게 "에이전트가 스스로 지킬 것"만 담는다.
- **작은 모델에는 짧게**: 약한 모델은 긴 지침을 따르지 못한다. 모델 등급(level)에 따라 지침을 2단계(짧은 것/전체)로 나눈다.
- **효과는 측정해서 정한다**: 평가 하네스(P0-1)로 지침 있음/없음을 같은 모델·작업에서 비교한다. 이득이 없으면 넣지 않는다. 실제 측정은 아직 하지 않았다.
- 사용자가 프로젝트에 `AGENTS.md`를 두었다면 그것이 우선한다(프로젝트 요약에 이미 들어감).

## 하지 않는 것
- 외부 SKILL.md/스크립트를 내려받아 실행하거나 JetAI에 번들하지 않는다(공급망 위험).
- "지침을 어기면 삭제하고 처음부터" 같은 강한 어조는 가져오지 않는다(약한 모델이 혼란스러워함, 근거 없음).
- 측정 전에는 지침이 품질을 높인다고 단정하지 않는다.
